# ADR-014 단어·용어 점진 정제 정책

## Status

ACCEPTED

## 배경

BaseKit에는 공통표준단어 3,284건과 공공표준용어 13,176건의 원본 데이터가 있다. 개인이 전체 데이터를 먼저 정제하면 시스템 공통 기능과 업무 모듈 개발이 장기간 중단될 수 있다. 표준화가 개발을 지원해야 하며 표준화 자체가 개발 진행을 막는 별도 대형 프로젝트가 되어서는 안 된다.

## 결정

전체 단어·용어를 선행 정제하지 않는다. 기능과 DB를 설계하면서 실제 사용되는 항목부터 우선 정제하는 Just-in-Time 방식을 사용한다.

```text
기능 WBS 선정
  → 필요한 Table·Column 후보 추출
  → 사용 단어·용어 우선순위 등록
  → 자동 분해·유사어·도메인 후보 제안
  → 필요한 항목만 검수
  → DDL·API·화면 계약 확정
  → 사용 빈도와 영향도에 따라 다음 정제 대상 선정
```

## 정제 상태

| 상태 | 의미 | 허용 범위 |
|---|---|---|
| IMPORTED | 외부 원본 반입 | 조회·검색·후보 분석 |
| PROVISIONAL | 개발에서 임시 채택 | Prototype, 화면·Mock, DDL 초안 |
| REVIEWING | 논리명·약어·도메인 검토 중 | 개발 초안과 영향 분석 |
| APPROVED | 검수 완료 | 배포 DDL, 공식 API·DTO·Interface 계약 |
| HOLD | 결정 보류 | 신규 배포 계약 사용 금지 |
| RETIRED | 폐기·대체 | 신규 사용 금지, 기존 영향 추적 |

## 단계별 Gate

### 화면·Mock Prototype

- `PROVISIONAL` 용어 사용을 허용한다.
- 미등록 단어는 자동으로 후보 Queue에 등록한다.
- 화면에 임시 상태를 표시하고 공식 표준으로 오인하지 않게 한다.

### DB 설계와 DDL 초안

- `PROVISIONAL` 또는 `REVIEWING` 용어로 DDL 초안을 생성할 수 있다.
- 미검수 항목과 도메인 충돌을 Warning 목록으로 함께 출력한다.
- 초안 DDL은 운영 배포용으로 표시하지 않는다.

### 배포 계약 확정

- 신규 Table·Column, API, Interface에 사용하는 용어는 `APPROVED`여야 한다.
- 예외가 필요하면 사유·영향·담당자·승인자를 기록한다.
- 승인 후 물리명과 도메인 변경은 Impact Register를 통해 관리한다.

## 우선순위

전체 가나다순이 아니라 실제 개발 가치와 영향도를 기준으로 정제한다.

1. 현재 WBS에서 생성할 Table·Column
2. BaseKit 공통 감사·사용자·메뉴·권한·코드 필드
3. 여러 Program에서 반복 사용하는 용어
4. 외부 Interface와 고객 계약에 노출되는 용어
5. 유사어·동음이의어·금칙어 충돌 항목
6. 나머지 미사용 원본 데이터

## 개인 작업 부하 절감

- 정확히 일치하는 공공표준 항목은 일괄 검토 후보로 묶는다.
- 용어 자동 분해와 마지막 도메인 단어 검사를 활용한다.
- 유사어·금칙어·중복 약어만 예외 Queue로 올린다.
- 사용처 수와 다음 WBS를 기준으로 검수 목록을 자동 정렬한다.
- 한 번에 전체를 처리하지 않고 기능 단위 Batch로 승인한다.
- 정제 완료 건수보다 실제 개발에서 재사용된 승인 용어 수를 관리 지표로 사용한다.

## 개발자 규칙

- 개발자는 DB에 임의 컬럼을 먼저 추가하지 않고 용어 후보를 등록한다.
- 개발 중에는 `PROVISIONAL`을 사용할 수 있으므로 정제 대기 때문에 Prototype을 중단하지 않는다.
- 배포 전 Gate가 미승인 용어와 직접 추가된 컬럼을 검출한다.
- 승인된 용어의 물리명·도메인을 변경할 때는 영향 대상과 재테스트 범위를 기록한다.

## 결과

표준화와 기능 개발을 병행할 수 있다. 초기 데이터 전체의 완전성을 요구하지 않으면서 실제 사용되는 영역부터 표준 품질이 높아지고, 배포 시점에는 검수 완료된 계약만 남도록 통제한다.
