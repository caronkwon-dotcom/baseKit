## 목적

1차 화면안과 SD/COMMON 인계 문서를 기준으로 실제 구현 전 UX 흐름을 더 명확하게 정리한다. 이번 작업은 기존 설계 방향을 변경하는 것이 아니라, 제품 화면에서 사용자가 상태와 다음 행동을 오해하지 않도록 프로토타입과 관련 문서를 보강하는 작업이다.

## 작업 범위

### 1. 상단 단계 구조 보완

현재 5단계 `Excel Preview → 분석 입력 → 실제 분석 상태 → 결과 검토·확정 → 생성 확인·결과` 구조를 제품 UI 기준으로 재검토한다.

권장 제품 흐름은 다음 4단계다.

1. 요구사항 준비
2. 분석
3. 결과 검토
4. 확정·생성

`분석 중 / 실패 / 완료`는 독립 업무 단계가 아니라 `분석` 단계 내부의 상태로 표현한다.

프로토타입 설명용 화면 구분은 유지할 수 있으나, 실제 제품에서 별도 Wizard 단계처럼 보이지 않도록 화면 구조와 문구를 조정한다.

### 2. STALE 상태 명시

요구사항 선택, 요구사항 원문 버전, 개별 설계자 의견, 종합 의견 등 분석 입력에 영향을 주는 값이 변경되면 기존 분석 결과를 삭제하지 않고 보존하되 `이전 입력 기준 결과` 상태로 전환한다.

화면에 다음 의미가 명확히 보여야 한다.

- 요구사항 또는 설계 의견이 변경됨
- 현재 결과는 이전 입력 기준임
- 재분석 필요
- STALE 상태에서는 후보 선택/확정/생성 불가
- `다시 분석`이 다음 주요 행동으로 제공됨

예시 문구:

> 요구사항 또는 설계 의견이 변경되었습니다. 현재 분석 결과는 이전 입력 기준입니다. 다시 분석한 후 확정할 수 있습니다.

STALE 화면 상태를 `SD-UX-wireframes.html`에서 실제로 확인할 수 있도록 추가한다.

### 3. 분석 결과 구조 가시화

현재 후보 중심으로 보이는 결과 화면을 보강하여 LLM 분석 결과의 전체 구조가 화면에서 드러나도록 한다.

결과 Workspace에 최소 다음 영역을 표현한다.

- 요약
- 업무메뉴·역할·액션
- 프로세스
- Layout 추천
- SD 프로그램 후보

가능하면 기존 `BaseTabs` 사용을 전제로 표현한다.

핵심 흐름이 화면만 보아도 다음처럼 읽혀야 한다.

`요구사항 → LLM 분석 → 업무구조/프로세스/Layout → SD 프로그램 후보 → 사용자 선택·확정 → 생성`

후보 상세에서는 LLM 원본과 사용자 편집본의 구분, 출처 요구사항, 수정 시 확정 해제 상태를 계속 유지한다.

## 유지해야 할 기존 원칙

- 기존 공통 컴포넌트 우선 사용
- 실제 진행률 계약이 없으면 퍼센트 표시 금지
- LLM 성공 후 자동 확정/자동 생성 금지
- 기본 생성 후보 선택 0건
- 사용자 확정 이후에만 생성 가능
- 생성 성공 건 재생성 금지
- 일부 실패 시 실패 건만 재시도
- 응답 유실/불명 상태에서는 먼저 상태 조회
- 새 요청으로 전체 재생성하지 않음
- 시스템 관리 Program/Runtime/권한과 SD 설계 프로그램 생성은 분리
- 신규 API/영속 모델/Action Code를 DESIGN이 임의 확정하지 않음

## 수정 대상

최소 다음 산출물을 검토하고 필요한 부분만 갱신한다.

- `UX-review.md`

`COMMON-UX-requests.md`는 이번 3개 보완 사항으로 COMMON 추가 요청이 생길 때만 수정한다.

## 검증

작업 후 다음을 확인한다.

1. 4단계 제품 흐름이 화면에서 자연스럽게 읽히는가
2. 분석 중/실패가 독립 업무 단계가 아니라 분석 상태로 이해되는가
3. 입력 변경 후 STALE 상태와 재분석 행동이 실제 프로토타입에서 확인되는가
4. STALE 상태에서 확정/생성이 차단되는가
5. 결과 화면에 업무구조/프로세스/Layout/프로그램 후보가 구분되어 보이는가
6. 기존 SD-UX-handoff 데이터·상태 계약과 충돌하지 않는가
7. UX-review에 STALE 및 결과 구조 검수 항목이 누락되지 않는가
