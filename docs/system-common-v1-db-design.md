# 시스템 공통 V1 DB 설계

## 상태

`STRUCTURE APPROVED - 상세 논리 모델 및 용어 검토 중`

`frontend/meta/schema-tables.json`과 `시스템관리 > 테이블관리` 화면에서 설계 초안을 검수한다. 실제 PostgreSQL DDL/Flyway Migration은 아직 생성하지 않았다.

이 문서는 시스템 공통 V1의 논리 구조와 권한 경계를 먼저 확정하기 위한 설계안이다. 용어와 도메인이 승인되기 전에는 운영 Migration 또는 JPA Entity를 생성하지 않는다.

## 1. 설계 목표

- 회사, 시스템, 조직, 직무, 사용자와 계정을 공통 기준정보로 관리한다.
- 구매시스템을 기준으로 내부 사용자와 공급업체 외부 사용자를 명확히 구분한다.
- 메뉴는 탐색, 프로그램은 실행, 액션은 프로그램 내부 행위로 유지한다.
- 권한은 `ROLE × PROGRAM × ACTION_CODE`로 판단한다.
- 외부 사용자는 역할 권한과 별개로 자신이 소속된 공급업체 데이터 범위를 벗어날 수 없게 한다.
- 테이블과 컬럼은 승인 용어를 사용하며 미등록 용어는 용어 확정 절차를 먼저 거친다.
- 물리 테이블명은 `B + 모듈 2자리 + 테이블 코드 4자리`의 7자리 규칙을 사용하고 SQL Alias는 마지막 4자리로 고정한다.

## 2. 용어 적용 Gate

```text
논리 테이블·컬럼 후보 작성
  → terms.json 정확 일치 확인
  → 없으면 words.json 단어 확인
  → 단어 상태·유사어·약어 충돌 확인
  → 마지막 도메인 단어와 domains.json 확인
  → PROVISIONAL 용어 후보 등록
  → 사용자 검토·확정
  → APPROVED 후 DDL·API 계약 사용
```

현재 발견된 주요 불일치는 다음과 같다.

- 코드에는 `USER_TYPE_CODE`가 있으나 용어집에는 `USER_TYPE`만 존재한다.
- 코드에는 `COMPANY_ID`가 있으나 용어집에는 `COMPANY_CODE`, `COMPANY_NAME`만 존재한다.
- 공공표준 단어는 `회사=CO`, `프로그램=PRGRM(폐기)`를 제시하지만 현재 BaseKit 계약은 `COMPANY`, `PROGRAM`을 사용한다.
- `공급업체`는 BaseKit 프로젝트 승인 단어 `VENDOR`를 사용한다.

따라서 공공표준 약어를 기계적으로 적용하지 않고 BaseKit 기존 계약, 개발자 이해도, 고객사 전환 영향을 함께 검토한다.

## 3. 사용자 구조 추천안

### 3.1 공통 사용자와 계정 분리

`사용자`는 사람의 공통 프로필이고 `사용자계정`은 로그인과 보안 상태다. 한 사람이 향후 SSO, 로컬계정 등 복수 인증수단을 가질 수 있으므로 V1부터 책임을 분리한다.

```text
사용자
  ├─ 사용자계정
  ├─ 내부사용자배정 → 회사 / 조직 / 직무
  └─ 공급업체사용자배정 → 공급업체
```

`사용자구분코드`는 우선 다음 두 값을 사용한다.

| 코드 | 의미 |
|---|---|
| `INTERNAL` | 구매사 임직원과 내부 운영자 |
| `VENDOR` | 공급업체 소속 외부 사용자 |

`PARTNER`, `EXTERNAL`, `SUPPLIER`를 동시에 사용하지 않는다. 구매시스템 V1에서는 `VENDOR`로 통일하고, 향후 고객·협력사·대행사 등 다른 외부 주체가 필요할 때 확장한다.

### 3.2 배정 테이블 분리 이유

하나의 사용자소속 테이블에 회사, 조직, 공급업체 컬럼을 모두 Nullable로 넣는 방식은 피한다.

- 내부 사용자 배정은 회사·조직·직무 관계를 가진다.
- 공급업체 사용자 배정은 공급업체와 계약상 유효기간을 가진다.
- 서로 다른 FK와 검증 규칙을 DB 구조에서 분명하게 표현한다.
- 한 사용자가 복수 회사 또는 복수 공급업체에 배정되는 확장도 가능하다.

## 4. V1 논리 테이블

### 4.1 조직·사용자 기준정보

| 논리 테이블 | 책임 | 주요 논리 컬럼 | 관계 등급 |
|---|---|---|---|
| 시스템 | BaseKit에 등록된 업무시스템 | 시스템ID, 시스템코드, 시스템명, 사용여부 | 기준정보 |
| 회사 | 내부 법인·사업회사 공통정보 | 회사ID, 회사코드, 회사명, 회사구분코드, 사용여부 | 기준정보 |
| 조직 | 내부 조직계층 | 조직ID, 회사ID, 상위조직ID, 조직코드, 조직명, 조직레벨, 사용여부 | 회사 REQUIRED, 자기참조 RECOMMENDED |
| 직무 | 사용자에게 부여하는 업무 직무 | 직무ID, 직무코드, 직무명, 사용여부 | 기준정보 |
| 공급업체 | 구매시스템 외부 거래주체 | 공급업체ID, 회사ID, 공급업체코드, 공급업체명, 상태코드 | 회사 REQUIRED |
| 사용자 | 내·외부 사람 공통 프로필 | 사용자ID, 사용자명, 사용자구분코드, 이메일, 언어코드, 시간대ID, 상태코드, 사용여부 | 기준정보 |
| 사용자계정 | 인증·잠금·비밀번호 상태 | 계정ID, 사용자ID, 로그인ID, 계정유형코드, 잠금여부, 로그인실패수, 비밀번호변경일시, 계정만료일시 | 사용자 REQUIRED |
| 내부사용자배정 | 내부 사용자의 회사·조직·직무 소속 | 내부사용자배정ID, 사용자ID, 회사ID, 조직ID, 직무ID, 기본여부, 유효시작일자, 유효종료일자 | 모두 REQUIRED/RECOMMENDED |
| 공급업체사용자배정 | 외부 사용자의 공급업체 소속 | 공급업체사용자배정ID, 사용자ID, 공급업체ID, 기본여부, 승인상태코드, 유효시작일자, 유효종료일자 | 사용자·공급업체 REQUIRED |

`공급업체`는 `회사`의 외부 거래처 확장정보로 본다. 이름·사업자 정보 등 공통 조직정보는 회사에 두고, 구매 평가·거래 상태 등 공급업체 전용 속성은 공급업체에 둔다.

### 4.2 메뉴·프로그램·권한

| 논리 테이블 | 책임 | 주요 논리 컬럼 | 관계 등급 |
|---|---|---|---|
| 프로그램 | 실행·MDI·권한 단위 | 프로그램ID, 시스템ID, 프로그램키, 프로그램명, 화면유형코드, 사용여부 | 시스템 REQUIRED |
| 메뉴 | 최대 3Depth 탐색계층 | 메뉴ID, 시스템ID, 상위메뉴ID, 프로그램ID, 메뉴키, 메뉴명, 메뉴레벨, 메뉴유형코드, 표시순서, 사용여부 | 시스템 REQUIRED, 상위메뉴 RECOMMENDED |
| 액션 | 프로그램에서 수행할 수 있는 행위 | 액션ID, 액션코드, 액션명, 사용여부 | 기준정보 |
| 프로그램액션 | 프로그램이 제공하는 액션 | 프로그램액션ID, 프로그램ID, 액션ID, 표시순서, 사용여부 | 양쪽 REQUIRED |
| 역할 | 시스템별 권한 묶음 | 역할ID, 시스템ID, 역할코드, 역할명, 사용자구분코드, 데이터범위코드, 사용여부 | 시스템 REQUIRED |
| 역할프로그램액션 | 역할별 허용 행위 | 역할프로그램액션ID, 역할ID, 프로그램액션ID, 허용여부 | 양쪽 REQUIRED |
| 사용자역할 | 사용자의 시스템별 역할 배정 | 사용자역할ID, 사용자ID, 역할ID, 유효시작일자, 유효종료일자 | 사용자·역할 REQUIRED |

역할의 `사용자구분코드`는 우선 `INTERNAL`, `VENDOR`, `COMMON`을 허용한다. 내부 전용 역할을 공급업체 사용자에게 배정하거나 반대로 배정하는 것을 Application과 DB 검증 대상으로 삼는다.

## 5. 권한 판단 순서

```text
1. 사용자계정 사용·잠금·만료 확인
2. 사용자 상태와 사용자구분 확인
3. 유효한 내부/공급업체 배정 확인
4. 사용자 역할의 사용자구분 적합성 확인
5. ROLE × PROGRAM × ACTION_CODE 확인
6. 사용자구분별 데이터 범위 적용
7. Backend API에서 최종 재검증
```

### 내부 사용자

- 역할에 따라 전사, 회사, 조직, 본인 범위를 가질 수 있다.
- 다중 회사 소속이면 현재 업무회사 Context를 명시적으로 선택한다.
- 역할만으로 다른 회사 Context를 임의 생성할 수 없다.

### 공급업체 외부 사용자

- 유효한 공급업체사용자배정이 필수다.
- 모든 구매업무 조회·변경에 서버가 공급업체ID 조건을 강제한다.
- Frontend에서 전달한 공급업체ID를 신뢰하지 않고 로그인 Context에서 결정한다.
- 공급업체 관리자 역할은 자기 공급업체 사용자 관리 범위만 가진다.
- 내부용 프로그램과 액션은 역할 배정 단계부터 차단한다.

## 6. 데이터 범위 V1

| 코드 | 내부 사용자 | 공급업체 사용자 |
|---|---|---|
| `ALL` | 시스템 전체. 제한적 관리자만 허용 | 금지 |
| `COMPANY` | 현재 업무회사 | 금지 |
| `ORGANIZATION` | 현재 조직과 승인된 하위조직 | 금지 |
| `VENDOR` | 공급업체 담당자 업무에 한해 지정 공급업체 | 로그인 사용자의 공급업체로 강제 |
| `SELF` | 본인 생성·담당 데이터 | 본인 데이터 |

데이터 범위는 버튼 노출 권한과 별개다. 같은 `SEARCH` 액션을 보유해도 내부 구매담당자와 공급업체 사용자의 조회 SQL 조건은 달라야 한다.

## 8. V1에서 제외

- 비밀번호 자체 저장 방식과 암호화 상세
- SSO/OAuth/다중 Identity Provider 구현
- 조직 겸직·파견의 급여/인사 상세
- 공급업체 계약·평가·품목 전체 모델
- 컬럼 단위 권한과 복잡한 ABAC Rule Engine
- 고객사별 확장속성 엔진
- 이력·Audit·Outbox 상세 구현

## 9. 승인된 결정

1. 물리명은 BaseKit 개발자가 이해하기 쉬운 영문(`COMPANY`, `VENDOR`, `PROGRAM`)을 우선한다.
2. 직무 물리명은 `JOB`을 사용한다.
3. 권한 행위 식별자는 `ACTION_CODE`로 통일한다.
4. 공급업체는 회사의 1:1 확장으로 유지한다.
5. 한 사용자의 내부·공급업체 구분은 V1에서 상호배타적으로 강제한다.
6. `회사ID`, `공급업체ID`, `직무ID`, `사용자구분코드`, `액션코드`를 BaseKit 용어로 승인한다.
7. 시스템 공통 테이블은 `BSYXXXX` 7자리 물리명을 사용하고 `XXXX`를 기본 SQL Alias로 사용한다.
8. 논리명·Full Name·4자리 코드를 Schema Catalog에서 함께 관리한다.

## 10. 다음 단계

1. 위 5개 구조 결정을 승인한다.
2. V1 전체 컬럼 후보를 논리명으로 확장한다.
3. 사용 용어를 `기존 승인 / 승인 후보 / 단어 누락 / 도메인 누락`으로 분류한다.
4. 필요한 단어·용어·도메인만 점진 검수한다.
5. 승인된 논리 모델로 ERD와 관계 등급을 확정한다.
6. 이후에만 Flyway V2 초안과 JPA Entity를 작성한다.
